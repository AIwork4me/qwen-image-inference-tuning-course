# M1 — 先测量：冻结基线

**学习目标（学完本课你能够）：**
1. 设计并运行一个可复现的基线协议，解释 cold/warmup/measured/fresh 四段结构各自的用途；
2. 用自己的记录计算热态中位数与离散度，并与参考战役对比；
3. 精确分解 fresh − warm = 0.90 s 的构成（TE 0.56 s + 调度方差 ~0.34 s），拒绝过度解释；
4. 论证"可复现性是测出来的属性，不是假设"——用两个独立会话的数据说话。

中文对照课：本文件即中文完整版；英文版见 [LESSON.md](LESSON.md)。

**问题。** "感觉慢"不是工程表述。任何优化之前，你需要一个数字，它 (a) 定义精确到
可以重新测量，(b) 可复现，(c) 对用户而言诚实地反映"快"的含义。这个数字就是基线
B0——而大多数性能错误恰恰发生在*这里*，在任何优化存在之前。

**概念（初学者术语表）。**

| 术语 | 通俗含义 |
|---|---|
| **基线（B0）** | 未优化但*功能完整*的配置：bf16 权重、40 步去噪、euler/simple、CFG 1、服务端默认注意力路径 |
| **热态运行（warm）** | 一切（权重、文本编码结果）均已缓存的重复生成——度量稳态吞吐 |
| **冷态运行（cold）** | 第一次生成：支付从磁盘加载模型的成本 |
| **新提示词运行（fresh）** | 换一个新提示词：击穿文本编码缓存，让真实 TE 成本显形 |
| **中位数与离散度** | 排序后重复运行的中间值，及其分散程度——离散度决定中位数是否可信 |
| **节点缓存（node cache）** | ComfyUI 会记忆相同计算；同提示词+同种子 = 瞬间重放（一个测量陷阱，见下） |

B0 刻意*不是*一个慢速兜底：父 Windows 项目被迫强制 math-attention 是*bug 绕行*
（他们的 flash 路径是坏的）；Linux 上正常路径可用，所以基线就是正常路径。服务端
日志证明实际跑的是哪条（"Using pytorch attention"）——相信日志，不要相信标志位。

**运行。**

```bash
# 课堂冒烟（有界，约 3 分钟 GPU）：一个提示词、一次测量运行
.venv-lab/bin/python -m lab baseline --smoke --date m1-smoke

# 正式会话（W7900 级显卡约 16 分钟 GPU）：完整协议
.venv-lab/bin/python -m lab baseline --date m1-$(date +%m%d)
```

GPU 额度说明：正式协议共 16 次运行（1 冷 + 1 预热 + 每提示词 3 次测量 × 3 提示词
+ 3 次新提示词）≈ 16 分钟。冒烟足以学会操作流程；只有正式会话产出的中位数才允许
对外引用。

**观察（真实输出，来自 2026-11-04 的 Radeon Cloud W7900 级实例的完整会话——正是
本课程随附的那次会话）。**

```
  cold          p1-zh-scene seed=1000042 total=95.583s ks=56.478s te=1.421s vae=1.256s steps=40 vrampeak=17305.8MB dev=17757.5MB
  warmup        p1-zh-scene seed=2000042 total=55.155s ks=53.815s te=0s    vae=0.901s steps=40 vrampeak=15809.2MB dev=17812.0MB
  measure       p1-zh-scene seed=42      total=55.188s ks=53.824s te=0s    vae=0.898s steps=40 vrampeak=15809.2MB dev=17812.0MB
  measure       p2-en-scene seed=42      total=55.098s ks=53.687s te=0s    vae=0.899s steps=40 vrampeak=33139.4MB dev=35105.3MB
  ...
  fresh_prompt  p1-zh-scene seed=42      total=55.709s ks=53.911s te=0.512s ...
```

在任何优化出现之前，注意三件事：热态运行的 `te=0`（文本编码节点缓存命中——所以
要有新提示词臂）；冷态 **95.6 s vs 参考主机 74.2 s**——云实例从 loop 挂载的持久
存储加载权重，比实验室本地盘慢，这是你的记录如实捕获的*平台*属性；VRAM 列在
提示词之间不同（ComfyUI 在冷运行后把 17.5 GB 文本编码器换出，p2 时又驻留回来——
内存管理本身是个变量，所以汇总报告逐记录峰值及其最大值）。

协议的形状，以及为什么：

```
cold (seed+1M) -> warmup (seed+2M) -> 3x measured (冻结种子) -> fresh-prompt 臂
```

- **cold** 只付一次模型加载，因此永不污染稳态数字；
- **warmup** 用与 cold *不同*的种子——否则 TE 节点缓存把预热变成空操作（本项目
  真踩过的坑）；
- **measured** 轮转冻结种子 [42, 1337, 20261030]；
- **fresh-prompt 臂**（追加" ."）击穿 TE 缓存，让真实文本编码成本显形。

**解释。** 参考战役的实测结果（2026-11-03）：

| 指标 | 数值 |
|---|---|
| 热态总时（中位数，两个独立会话共 18 次） | **55.21 s**（两会话：55.24 / 55.21） |
| 稳态步时 | 1.345 s（离散 1.336–1.367） |
| 新提示词总时 | 56.10 s |
| ——其中文本编码（fresh 臂实测） | 0.56 s 中位（单次范围 0.31–0.60 s） |
| ——其中残余（排队/调度方差，不是 TE） | ~0.34 s |
| 完整冷启动 | 74.2 s（服务端启动 7.0 s 另计） |
| 峰值 VRAM（设备级，采样） | 37.7 GB |

精确地读 fresh 分解：**fresh − warm = 0.90 s**，其中*实测* TE 贡献 0.56 s（中位）
——剩下约 0.34 s 是运行间调度方差，不是文本编码。只说"fresh 增加了 TE 成本"
会把增量少解释三分之一。

我们跑了两个完整会话——不是因为怀疑第一个，而是因为**可复现性是测出来的属性，
不是假设**。你的实例在 W7900 级 GPU 上应接近这些数字（上面那次云实测：
55.17–55.24 s）；不同的 Radeon 卡合法地不同——你的记录捕获的是你实际的 GPU，
这正是其诚实所在。

记录去向：`runs/<tag>-B0/*.json`（记录）与 `runs/raw/<tag>-B0/*.png`（图像，留在
你的主机——其 SHA256 在记录里）。聚合*你的*数字：

```bash
.venv-lab/bin/python -m lab report --scope student --write
```

它写出 `runs/SUMMARY.md`——`evidence/results/` 下冻结战役的 SUMMARY 永远不会被
这个命令触碰。

**思考（答案在 `<details>` 中）。**

1. 为什么热态中位数不是"用户体验"？什么才是？
   <details><summary>答案</summary>用户通常支付偏冷成本（服务器热但提示词新）：
   新提示词总时是最接近的单个数字，而 cold+boot 对首请求 SLA 重要。热态只对
   重复工作的稳态吞吐是正确口径。</details>
2. 两个参考会话相差约 0.03–0.13 s。这是噪声吗？你怎么判定？
   <details><summary>答案</summary>与*会话内*离散度比（每步 1.336–1.367 s ⇒ 总时
   上约 0.03 s 在运行噪声内）。会话间差距量级 = 会话内离散 = 测量一致。另外：
   相同种子产出比特级相同图像（噪声底 0.0000），所以时间方差是调度器/主机噪声，
   不是模型噪声。</details>
3. 为什么我们记录*实际使用的注意力后端*而不是传入的标志位？
   <details><summary>答案</summary>标志位可能静默失效（后端不可用→回退）。抓取的
   日志行才是执行真相；标志位只是意图。证据 > 意图。</details>
4. 如果你在会话中途"改进"了运行器，什么会被破坏？
   <details><summary>答案</summary>下游一切：轮询间隔改变测量开销，新提示词/种子
   改变负载，服务端标志改变被测对象。冻结协议 = 可比的 A/B；改动放进一个
   *新*实验和它自己的记录。</details>

**学生练习（按难度分层）。**
- 入门：跑冒烟会话，在 `runs/` 里找到你的记录，指出 `total_s`、

  验收：四个字段各附一句解释（step[0] 为何被排除？——它带着 TE + 权重恢复成本）。
- 进阶：用 `report --scope student --write` 聚合你的数字，写一段对比：你的中位数、
  离散度 vs 参考战役 55.21 s / 1.336–1.367 s，判断你的主机是否属于同一测量总体。
  提交：对比段落 + SUMMARY 摘录。
- 挑战：只用自己的记录，复现 fresh − warm = 0.90 s 的三段分解（TE、调度残余、
  不确定性），并说明哪一段在你的主机上无法分离。提交：分解表 + 方法说明。

**研究延伸（可检验的假设）。** 假设：在本课程的技术栈上，把测量轮询间隔从当前值
降到 50 ms 会把热态总时的测量偏差压低到 0.05 s 以内，从而让 <1% 的真实改善变得
可检。先推导当前轮询造成的量化误差上界，再设计 n≥9 的实验检验，并预测新噪声底。
