# M2 — 剖析：时间到底去哪儿了

**学习目标（学完本课你能够）：**
1. 用两层剖析（流水线计时 + 内核追踪）定位推理负载的真实热点，并说明每层数据的来源与盲区；
2. 用 Amdahl 公式从剖析数据计算优化上界，把它当作预测（planning）而非结果；
3. 区分"实测（measured）"与"推导（derived）"数字，并在表格中逐项标注；
4. 陈述 97.8% GPU-busy 能证明什么、不能证明什么（排除空闲 ≠ 证明计算受限）。

中文对照课：本文件即中文完整版；英文版见 [LESSON.md](LESSON.md)。

**问题。** 你有了基线（55 s）和按小时计的 GPU 额度，而不是几周时间。先做哪项优化？
瞎猜浪费额度；剖析在任何花费之前就给机会*排序*——还告诉你面对的究竟是哪类问题
（计算受限？访存受限？调度受限？）。

**概念（初学者术语表）。**

| 术语 | 通俗含义 |
|---|---|
| **剖析（profiling）** | 记录时间去了哪里——哪个流水线级、哪个 GPU 内核 |
| **DiT（扩散 Transformer）** | 执行 40 步去噪的网络——真正"画画"的角色 |
| **内核（kernel）** | GPU 上启动的一个工作单元（一次矩阵乘、一次注意力） |
| **GEMM** | 通用矩阵乘——Transformer 的算术心脏 |
| **注意力（attention）** | "环顾全局、按相关性加权"的算子；成本随序列长度增长 |
| **GPU-busy %** | 墙钟时间里 GPU 正在执行内核的比例（vs 空闲/等待） |
| **Amdahl 定律** | 若某部分占时间比例 f、被加速 s 倍，总加速 = 1 / ((1−f) + f/s)——不变的部分封顶 |
| **实测 vs 推导** | 仪器报告的数字 vs 由其他数字算出的数字——永远标注是哪种 |

**运行。**

```bash
# 课堂（约 2 分钟 GPU）：仅 A 层——从你的 B0 记录提取流水线计时
.venv-lab/bin/python -m lab profile --layers pipeline --date m2-pipe

# 完整会话（约 12 分钟 GPU）：加 B 层——有界的 rocprofv3 内核追踪
.venv-lab/bin/python -m lab profile --date m2-full
```

GPU 额度说明：B 层要在*剖析器包裹下*启动服务端两次（DiT 窗口 + TE 窗口，各 90 秒
采集）。被追踪的墙钟时间只用于构成分析——插桩带来约 1% 开销，因此被追踪的运行
**永远不构成**性能主张。

**观察（参考战役，2026-11-03；你的数字写入 `runs/<tag>-profile/`）。**

A 层——流水线计时（来自 B0 记录的 websocket 节点事件）：

| 阶段 | 时间 | 占比 | 方法 |
|---|---|---|---|
| DiT 去噪（40 步） | 53.88 s | **97.6%** | 实测（节点计时） |
| VAE 解码 | 0.90 s | 1.6% | 实测 |
| 文本编码器（fresh） | 0.56 s | ~1% | 实测（新提示词臂） |
| 其他（排队/保存/客户端） | 0.43 s | 0.8% | **推导**（减法） |

B 层——内核追踪（rocprofv3 挂在真实服务端进程上，对齐一次热态生成的 90 秒有界
窗口；追踪恰好包含 40.0 步 = 95,600 次内核分发）：

| 内核类别 | 分发次数 | GPU 时间 | 占繁忙比 |
|---|---|---|---|
| GEMM（`Cijk_Alik_Bljk…` hipBLASLt） | 8,021 | 32.54 s | **61.3%** |
| 注意力（`attn_fwd` flash） | 1,248 | 17.23 s | **32.4%** |
| 逐元素/激活 | 83,067 | 2.49 s | 4.7% |
| 归一化（adaln） | 2,573 | 0.71 s | 1.3% |
| **GPU 繁忙** | — | 53.11 / 54.31 s | **97.8%** |

另有：197 次memcpy API 调用（每次约 36 µs——每步的 sigma），**1 次同步**。

两条刻进实验代码的工具教训（各自付出过一次失败运行）：
- 必须对 rocprofv3 包装器发 **SIGINT**，否则得到未转换的 `.dat` 缓冲（修复前
  复现过两次）；
- 约 0.5 s 的 TE 阶段落在第一个追踪窗口之外——其成本改在 A 层测量。
  **清楚你的剖析器没有捕到什么。**

**解释。** 教训一：DiT 就是一切。把 VAE 解码从 0.9 s 优化到 0.0 s，端到端只改善
1.6%。

97.8% GPU-busy 能证明什么、不能证明什么：高繁忙比排除*空闲时间*——不存在大的
调度空隙，不存在"GPU 等主机"的救援空间。但它**不能**单独证明负载是*计算受限*：
GPU 可以 100% 繁忙地执行被显存带宽卡住的内核。区分计算受限与访存受限需要另一台
仪器（如 FLOP 利用率 vs 硬件峰值，或 roofline 分析）——我们没有运行。综合两层
我们*能*说的：时间集中在 GEMM + 注意力内核（占繁忙时间 93.7%），几乎没有拷贝与
同步，每步时间稳定——因此实际结论成立（不存在调度/传输救援；杠杆是更少/更快的
内核工作），而计算-vs-带宽问题保持开放。仪器显示多少，就陈述多少。

Amdahl 作为规划工具（不是结果——上界是*预测*，只有测量才是*结果*）：

- 注意力瞬间归零：e2e ≤ 55.2 × (1 − 0.324×0.976) ≈ **1.46×**
- 步数 40 → 8（等步成本）：约 **4.6×** 上界
- GEMM 快 2 倍：约 1.43×

这些上界为实验排了序（turbo ≫ int8 > 注意力）——后续测量在约 5% 内证实了它们
（实测 4.55× vs 上界 4.6×）。

**思考（答案在 `<details>` 中）。**

1. 计算"逐元素+归一化归零"的 Amdahl 上界。案例研究为何据此否决了 torch.compile？
   <details><summary>答案</summary>逐元素+归一化约占繁忙 6.0% ≈ e2e 的 5.9% ⇒
   上界 ≈ 1/(1−0.059) ≈ 1.063× ⇒ 55 s 上省不到 3.2 s，还没算编译预热成本与
   形状特化风险。数字见：
   `evidence/results/p2-profile-profile/rocprof-dit/analysis.json`
   （by_class 占比）。</details>
2. 追踪显示 97.8% GPU 繁忙。同事提议"把主机侧 PNG 保存与下一次生成重叠"。仅凭
   A 层估算上界。
   <details><summary>答案</summary>"其他"（排队/保存/客户端）占 e2e 的 0.8% ⇒
   完美重叠最多赚 0.43 s / 55 s（约 1.008×）。何况 ComfyUI 本就异步保存——这个
   想法花费的分析时间永远超过它的回报。</details>
3. 内核表说注意力 = 17.23 s。M4 的 F1 实验靠换注意力后端省了 10.7 s DiT 时间。
   为什么"注意力成本从 17.2 降到 6.5 s"要标注为推导估计而非测量？
   <details><summary>答案</summary>17.2 s 来自*追踪分类器*（在参考主机上实测）；
   6.5 s 是从另一台仪器（A/B 节点计时）减法推得的。当时没有对 ck 路径做追踪，
   所以 6.5 s 是与数据一致的估计，不是直接观测。（这正是实测-vs-推导纪律：
   `pipeline_breakdown.json` 现在带逐键 `method` 映射。）</details>

**研究延伸（可检验的假设）。** 假设：在 2048×2048 分辨率下，注意力占比将从 32.4%
显著上升（序列长度约 ×4），使"注意力后端"杠杆的排序超过 INT8。用 Amdahl 公式
预测新排序所需的占比阈值，并写出一个有界实验来检验（2048² 目前 BLOCKED 于
1024² 质量判定——说明该依赖关系）。
