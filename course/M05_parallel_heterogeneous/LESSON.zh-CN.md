**问题。** 市场话术里的并行很简单："把一部分工作搬到 CPU 上重叠起来！"工程上的
并行要靠测量。本模块把单 GPU 图像服务的两个诱人想法——把文本编码器搬到 CPU、
在 GPU 去噪时流水线化 CPU 工作——都测到有证据为止，其中一个交出了 14× 的*损失*，
却也是全课程证据最有教学价值的部分。

**概念（初学者术语表）。**

| 术语 | 通俗含义 |
|---|---|
| **异构计算** | 用不同类型的处理器（GPU + CPU）承担同一负载的不同部分 |
| **文本编码器（TE）** | 把提示词变成条件张量的 80 亿参数 Qwen3-VL 模型（bf16 约 17.5 GB） |
| **流水线（pipelining）** | 第 *i+1* 级的工作在第 *i* 级仍在运行时就开始（这里：GPU 去噪请求 *n* 时，CPU 编码请求 *n+1*） |
| **重叠（overlap）** | 两个处理器真正并发执行的时间——*只能用时间戳证明*，利用率图不行 |
| **吞吐 vs 延迟** | 每分钟图像数 vs 每张图像秒数——不同指标，赢家不同 |
| **争用（contention）** | 两个处理器共享一台主机时要抢显存带宽与操作系统线程——并行有代价 |
| **负结果** | 表明某方案*不可行*的测量——证据完整时是一等科学 |

**观察（参考战役——随附证据）。**

H1 —— 把 8B 文本编码器搬到 CPU？（经 `comfy.sd.load_clip` 的完全相同计算图）：

| | GPU | CPU |
|---|---|---|
| 编码（3 个提示词） | 0.35 / 0.61 / 1.17 s | **136.8 / 177.8 / 207.1 s** |
| VRAM 占用 | 16.8 GB | **0** |
| 条件一致性 | — | cosine ≥ 0.999999，max\|Δ\| ≤ 0.0074 |

H2 —— CPU 编码与 GPU 去噪重叠？（4 请求，turbo 8 步；B 臂经实验室自有定制节点
注入 CPU 预计算的条件）：

| | A 顺序执行 | B 流水线 |
|---|---|---|
| 4 图总时 | **51.1 s** | 737.1 s |
| 每分钟图像 | **4.69** | 0.33 |
| 已证实的重叠 | — | **50.4 s**（时间戳） |
| CPU 负载下的 GPU 生成 | 12–13 s | **19.1 s** |

**解释。** H1：正确性**通过**（条件数值等价）而延迟**失败**（慢 152–391×）。
8B 编码器是 GEMM 受限负载——恰是 GPU 的看家本领。CPU TE 是一笔 VRAM 交易
（−16.8 GB），在这个级别的主机上绝不是速度方案。

H2 一张表装了三条独立的教训：

1. **重叠是真实的**——50.4 s 的 CPU+GPU 并发执行，由逐请求时间戳证明，不是从
   利用率图推断。（为什么用时间戳：利用率可以 100% 而流水线照样输——下面的数字
   就是证明。）
2. **它仍然输 14×**——流水线的 CPU 侧每请求耗 160–221 s；Amdahl 对流水线同样
   成立（最慢的级门控全局）。
3. **并行有代价**——128 线程的 CPU 矩阵乘饿死了服务端的内核启动线程；*GPU*
   生成慢了 1.5×（12–13 s → 19.1 s）。共享一台主机的两个处理器会争用。

**吞吐 ≠ 延迟**：两个设计都不改变单张图像的 9–12 s。"并行更快"必须带名词——
更快*什么*？

什么才会有帮助（未测 = 公开挑战）：顺序快速生成（BEST ≈ 6.6 张/分，含新提示词）
是已测边界。唯一未测方向：把多张图**批处理**进一次去噪（batch_size > 1）——见
M7 挑战任务。

**思考（答案在 `<details>` 中）。**

1. 从 `H2_RESULTS.json` 推导流水线获胜所需的盈亏平衡 CPU 编码时间 t\*。参考主机
   离 t\* 有多远？
   <details><summary>答案</summary>稳态下，B 臂周期 = max(GPU 生成, CPU 编码) +
   交接；A 臂 = TE_gpu + 生成 ≈ 12.8 s。当 max(生成, t_cpu) < 12.8 s 时流水线获胜
   ⇒ t\* ≈ 12 s（设生成 ≈ 12 s 未受扰动——注意争用会*抬高*生成时间）。参考主机
   的 CPU 编码为 160–221 s：慢 13–18×，甚至还没算争用。</details>
2. 在 4× 更快的 CPU（或 int8 CPU TE）上，B 会赢吗？下结论前还必须重测什么？
   <details><summary>答案</summary>t_cpu ≈ 40–55 s 仍高于 t\*；约 8× 才接近
   盈亏平衡。但争用必须重测（线程饥饿随 CPU 负载变化），且 CPU 产出的条件必须
   重新通过一致性检查。这个主张需要新的成对 A/B——绝不是外推。</details>
3. 解释为什么"重叠期间 GPU 利用率 100%"不能证明流水线有效。
   <details><summary>答案</summary>利用率只说明 GPU 在忙——不说明*总量*缩小了。
   B 臂里 GPU 忙得*更慢*（生成 19.1 s vs 12–13 s），而 CPU 按自己的节奏爬行：
   100% 繁忙且差 14×。吞吐以端到端每分钟图像数计量，时间戳证明时间去哪了。
   </details>
4. 杀掉"把 TE 搬到 CPU"提案，你会引用 H1 表中的哪一个数字——必须附带什么但书？
   <details><summary>答案</summary>136.8–207.1 s vs 0.35–1.17 s（慢 152–391×）。
   但书：它*释放 16.8 GB VRAM*——在显存受限的卡上，这笔交易仍然可能是对的，
   代价是把延迟明明白白说在前面。</details>
