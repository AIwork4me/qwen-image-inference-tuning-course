# 优化研究方法论

**本课程的思维方式：测量 → 建模 → 假设 → 优化 → 验证 → 解释 → 复现 → 贡献。**

*本章是贯穿 M0–M7 所有模块的方法论主线。建议在 M1 之前通读一遍，M6 之后再读一遍。
本文引用的每一个数值都已登记在
[`data/verified_claims.json`](data/verified_claims.json)（含证据路径与适用范围）。*

English version: [METHODOLOGY.md](METHODOLOGY.md)

---

## 1. 一句话哲学

> 没有运行记录的性能数字不是结果；没有质量判定的加速不是交付。

优化不是一场寻找漂亮数字的狩猎，而是一门**定位瓶颈、控制变量、诚实测量**的工程学科。
负结果与正结果同样有价值——有时更有价值，因为负结果更少见、更少被人如实记录。

## 2. 优化研究闭环（每个模块都要回答的十个问题）

学习、提出或评审任何一项优化时，按顺序回答以下十问——**先自己作答，再看下一节的实测结果**：

| # | 问题 | 本课程在哪里回答 |
|---|---|---|
| 1 | **我们要解决什么真实问题？**（延迟/吞吐/显存，对谁是刚性约束？） | M1 基线动机；M5 部署故事 |
| 2 | **什么操作主导了成本？**（不是什么技术时髦，而是什么在关键路径上） | M2：DiT 占流水线 97.6%；GEMM 61.3% / 注意力 32.4%（占 GPU 繁忙时间） |
| 3 | **哪些测量支持这个诊断？** | M2 流水线+内核追踪；M5 请求时间戳 |
| 4 | **我们提出什么改变——属于三条策略中的哪一条？** | 见 §3 |
| 5 | **实现之前，预测加速上限是多少？**（Amdahl 上界；先写下来） | M3：预测 ≤4.63×；M5.1：预测 ≤1.07× |
| 6 | **哪些变量保持不变？**（一次一个变量；成对 A/B） | 每个模块的对照表 |
| 7 | **结果如何精确测量？**（冷/热、中位数/均值、样本数、负载） | M1 协议；判定词汇表 |
| 8 | **目标指标是否真的超越了噪声地改善？** | 每个模块的观察表 |
| 9 | **质量、显存与资源成本发生了什么？** | M6 质量门；M4 显存；M5 CPU/内存 |
| 10 | **别人如何复现并核验？**（运行 ID、种子、证据路径、PR） | M0 证据文化；M7 贡献 |

无法被测量证伪的假设不是工程假设。"先预测后测量"（第 5 问）正是把实验记录变成科学
的关键：先写出上界，再核对上界。

## 3. 让推理变快的三条路（也只有这三条）

本课程的每一项优化——以及业界大多数优化——都属于以下之一：

### ① 减少计算量（Less Computation）——删掉工作

不是把一个操作加速，而是把它删掉。步数蒸馏（去噪 40 → 8 步）删掉了 80% 的 DiT
计算：热态 **4.55×**（M3）。代价：调度表改变会合法地改变输出，因此这项收益是用一个
**必须由人裁决的质量决策**换来的——而且 Amdahl 把它压在 5× 以下（DiT 只占流水线的
97.6%），每步耗时并未变化（1.345 → 1.337 s：证明收益纯粹来自"少算"，不是"算得快"）。

### ② 加速计算（Faster Computation）——同样的工作，更快的内核

注意力后端切换（ck）：**1.22×**（F1）。INT8 权重量化：1024² 下 **1.08×**，但
**显存 −6.7 GB**——这是一笔"显存优先"的收益（F2）。纪律：硬件利用率百分比不是延迟；
只有成对的端到端测量才算数；**独立的加速比永远不能相乘**
（4.55 × 1.08 × 1.25 会"预测"出 6.14×；实测 6.12×——而 ck 在 int8-turbo 路径上
*毫无增益*：LF2 vs LF3 = 9.023 vs 9.022 s，分布完全重叠）。

### ③ 并行与异构计算（Parallel & Heterogeneous）——重叠或搬迁工作

当单个加速器已经饱和，就把工作搬到另一个引擎并重叠执行。本课程实测了那个诱人的版本
（CPU 文本编码与 GPU 去噪重叠），**损失 14×**（M5.0）——随后用 OpenVINO 重做实现
（M5.1），恢复到热态服务延迟 **1.081×** 改善、显存节省 **17.26 GB**，而实际批量吞吐
只改善 **1.029×**，因为新的瓶颈变成了编排开销而非编码本身。异构计算的回报恰好等于
被搬走的工作原来在关键路径上的占比，而你添加的每一次交接都会收费。

**三条策略只能通过测量来组合。** M6 的 BEST（6.12×）是 ①+② 的实测组合，
绝不是加速比的乘积。

## 4. 核心性能概念（每个都配本课程自己的实测数）

### 4.1 计算复杂度 vs 实测成本

复杂度（如注意力 O(n²·d)）告诉你成本*如何随规模增长*，不告诉你*会测到多少*。
M2 的内核追踪显示 GEMM 占繁忙时间 61.3%——理论指引了搜索方向，但只有追踪量化了它。
规则：复杂度负责论证，测量负责裁决。

### 4.2 显存容量 vs 显存带宽

容量是 GB，带宽是 GB/s。F2 的 INT8 把权重字节减半 → 解决了容量问题（−6.7 GB），
但 1024² 下 DiT 仍是计算受限，延迟几乎不动（1.08×）。当负载变成带宽受限（更大分辨率、
更长序列），同一个改动的回报会大得多。预测之前，先知道自己在哪个区间。

### 4.3 计算受限 vs 访存受限

一个数字就能判断：B0 期间 GPU 繁忙占比 **97.8%**（M2）——W7900 最多只有 2.2% 的
时间在等活干，因此任何主机侧微优化的上界只有约 1.02×。这正是 torch.compile 被
否决（NOT_RUN）的原因——它的上界（< DiT 的 6%）对*该负载、该技术栈*赚不回工程成本。

### 4.4 占用率与内核启动开销

大量小内核 → 启动/同步开销可能主导。M5.0 的 CPU 编码器饿死了 GPU 的启动线程：
CPU 编码负载下，GPU 生成从 12–13 s 慢到 19.1 s（约 1.5×）——这是任何单部件基准
测试都看不见的*争用*效应。

### 4.5 Amdahl 定律——本课程用得最多的公式

$$S(n) = \frac{1}{(1-p) + \frac{p}{n}}$$

加速比受限于改进所触及的时间占比 p，无论改进幅度 n 多大。本课程的实例：

- 步数 40→8（n=5）、p=0.976（DiT 占比）：上界 = 1/(0.024+0.1952) = **4.63×**；实测 4.55×。
- 编码器快 331–480×（n≈331+）、p≈0.04（编码占比）：上界 ≈ **1.04–1.07×**；实测热态服务 1.081×（计入交接后落在上界附近）。

Amdahl 定律保证了第 5 问（先预测）永远可以回答。

### 4.6 延迟 vs 吞吐——以及它们为何分道扬镳

延迟是一个请求者等待的时间；吞吐是批量场景下单位时间的出图数。M5.1 最尖锐的一课：
热态单请求服务延迟改善 **1.081×**（13.031 → 12.060 s），而实际四请求批量吞吐只改善
**1.029×**（4.42 → 4.55 张/分）。差额是请求间编排开销（预计算臂每请求多约 0.54 s）。
用服务时间求和算出的"张/分"是上界，必须标注为 naive（朴素值）。

### 4.7 冷启动 vs 热启动

冷 = 空闲后的第一个请求（加载模型、缓存为空）：BEST 冷态 32.4 s vs 热态 9.02 s。
热 = 模型常驻、缓存命中。永远不要把两个总体混合平均；永远不要拿冷臂对比热臂。
M5.1 的冷包含 1.33× 主要是*避免了 16.8 GB GPU CLIP 的重新加载*——这是会话启动效应，
不是稳态收益。

### 4.8 新提示词延迟（fresh-prompt latency）

"热"服务器面对新提示词仍要支付文本编码：B0 的新提示词总时间比热态多 0.90 s
（TE 0.56 s + 约 0.34 s 调度波动）。M5.1 的串行新提示词 C1b 估算是 12.58 s
（12.03 预计算 + 0.55 编码）。对一次性的 API 用户，这才是诚实的数字。

### 4.9 流水线充填与排空（fill and drain）

k 级流水线必须先充填才能饱和，结束前还要排空。M5.1 的 C 臂每批支付 0.56 s 充填
（首次 CPU 编码）；B 臂的充填是 176 s（首次 PyTorch CPU 编码）。批量越小，充填
摊销越差——4 请求批量的充填影响是 4/4，100 请求批量只有 4%。

### 4.10 CPU/GPU 重叠

重叠只有被时间区间证明才算数：M5.0 用逐请求时间戳证明了 50.4 s 的真实重叠——
却仍然损失 14×，因为重叠只在 CPU 级不是最慢生产者时才能隐藏 CPU 时间。B 的 CPU 级
（中位 147 s）比 GPU 级（12.07 s）慢 12 倍：整条流水线以 CPU 速度运行。

### 4.11 排队与编排开销

每次交接都要付费：HTTP 提交、排队等待、工作流解析、文件写入、完成轮询。M5.1 实测
预计算臂每请求多出约 0.54 s 编排开销——相对 12 s 的生成很小，但在批量层面吃掉了
服务收益的三分之二。编排是系统性能中真实、可测的组成部分（也是 course-v2 开销
研究的对象）。

### 4.12 内核加速 vs 端到端加速

一个内核快 1.25×（ck 作用于 DiT）只带来端到端 1.22×（VAE 与 TE 没有加速）。
一个编码器快 331–480×，只带来服务延迟 1.081×。差额永远是 Amdahl + 交接。
只报告端到端，否则什么都别报告。

### 4.13 量化：存储 vs 运算

本课程的 INT8 指 *INT8 存储权重*、混合精度执行——不是全程 INT8 运算。F2（INT8 DiT）
保真度近乎无损（LPIPS 0.005–0.031 vs 0.0000 噪声底）。M5.1 的 C2（INT8 编码器）却在
空负向条件门上以 28.25% relL2 失败：量化*不同部件*的爆炸半径天差地别。
说"INT8"时永远要说清*量化了什么*、*由哪个门*判定。

### 4.14 保真度 vs 感知相似度

保真度 = 与同臂自身参考的距离（INT8 vs BF16、同一调度表）：LPIPS 低意味着*量化是
忠实的*。相似度 = *不同*输出分布之间的距离（turbo vs 40 步）：LPIPS 0.19–0.30 意味着
*合法的不同图像*，本身不代表好坏。混淆这两种语义是本课程最常见的分析错误。

### 4.15 实验噪声与置信度

报告 n、中位数与离散度；绝不报告单次运行。本课程的噪声底：9/9 同种子 LPIPS 0.0000
（会话内确定性），但 B0 两个会话差 55.24 vs 55.21 s（0.06%）——在该技术栈上，
亚 1% 的"改善"就是噪声。当区间重叠（LF2 9.023 vs LF3 9.022），诚实的结论是
"无可测差异"，而不是"LF3 赢了"。

### 4.16 盈亏平衡与瓶颈迁移

每项优化都存在一个不再划算的工作点：0.53 s 的 CPU 编码器只有在去噪约 0.53 s 时
才占周期的 50%（实测约 12 s）。而每项成功的优化都会*迁移*瓶颈：M5.1 把瓶颈从
编码器搬到了编排 + GPU 去噪；下一个优化必须攻击*它们*，否则一无所获。

## 5. 负结果是一等公民的科学

本课程最核心的一条结果链是*失败 → 诊断 → 部分恢复 → 系统级教训*：

1. **M5.0（负结果）：** PyTorch CPU 文本编码器下放节省 16.8 GB 显存，却付出
   152–391× 的编码延迟，以及被时间戳证明重叠存在情况下 14× 的吞吐损失。
2. **M5.1（恢复）：** 更好的 CPU 实现（OpenVINO、常驻 worker、BF16 执行 IR）让
   CPU 编码变得可用：正提示词快 331–480×、条件张量 PASS、节省显存 17.26 GB。
3. **M5.1（天花板）：** 编码器收益 ≠ 系统收益。热态服务 1.081×，实际批量 1.029×，
   冷包含 1.33×——三个不同的问题，三个不同的数字，同一个 Amdahl 上界。
4. **仍在失败（保持诚实）：** C2 INT8 空负向门 **FAIL**（28.25%），FP32 存储 IR
   变体 **FAIL**（6.63%）——任何主观接受都不能提拔它们；40 步扫描保持 **NOT_RUN**。

这条链正是本课程存在的理由：它教会学生*架构决策是假设*，实现是处理手段，
而系统用你自己必须定义的单位记分。

## 6. 判定词汇与证据规则

- 状态词汇：`PASS / FAIL / BLOCKED / NOT_RUN / PENDING`——FAIL 只能通过重跑该门来
  清除，绝不能被主观接受或邻近的成功所清除。
- 主张 ≤ 证据：每个数字都引用运行记录路径；每份运行记录都带源 HEAD；
  登记表（[`data/verified_claims.json`](data/verified_claims.json)）是机器可读的索引，
  由 `scripts/course-quality/check_claims.py` 校验。
- 范围纪律：不同的运行总体（冷 vs 热）、内存定义（战役峰值 17.26 GB vs 平衡审计
  16.18 GB）、精度配置（FP16 存储-BF16 执行 vs FP32 存储）永远不可互换。
- 人工质量判定必须通过带评审人与适用范围的显式机制记录
  （见 `docs/release-closure/PR2_OWNER_QUALITY_VERDICT.md`），且绝不越出其声明的范围。

## 7. 从学生到贡献者

闭环的终点是贡献：Issue → 假设 → 复现器 → 代码 → 测试 → 证据 → PR → 评审。
M7 正是按这条路径打分的；PR 模板（`.github/PULL_REQUEST_TEMPLATE/optimization.md`）
要求写清瓶颈、改动、不变量、前后数字、质量影响、资源成本、可复现性与仍未验证的主张。
如果你能诚实地填满那份模板，你就完成——并且能够辩护——真正的优化工程。
